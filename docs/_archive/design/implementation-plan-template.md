## 本文档定位

这是一份 **plan，不是详细设计**。它负责讲清楚做什么、为什么、分几步推进，以及什么算完成；schema 字段、函数签名和具体文件改动留到对应阶段开工时确定。

它也是跨 session 的进度记录：新 session 先读「进度」，每完成一个阶段便更新状态，并在「变更日志」记录发生变化的原因。

写作约定：

- 每条原则或决策先用一句话写清主张，再补理由和边界。
- 同一论证只写一次，其他位置直接引用。
- 正文只保留当前有效结论；探索过程和被替代方案压缩进变更日志。
- 变更日志记录“为什么改、解决了什么”，不重复正文细节。

## 关键风险

- **[风险]** —— 触发信号：[可观察现象]；影响：[用户、数据或运维后果]；应对：[结构性预防、验证和失败处理]。
- **[风险]** —— 触发信号：[填写]；应对：[填写]。

风险判断规则：

- 先确认问题存在真实可达路径；不可达的理论缺陷不扩 scope 修复。
- 同形问题第二次出现时回看抽象边界，不继续增加白名单或兄弟特例。
- 修复复杂度接近功能本身时，重新评估范围和一致性承诺。
- 若一个机制只用于维持两份状态一致，优先统一真相源。
