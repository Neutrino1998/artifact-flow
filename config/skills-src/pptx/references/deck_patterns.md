# Deck 叙事结构

先选 deck 类型,再写大纲。不要把用户给的材料按原顺序机械分页。

## 通用骨架

1. 开场:一句话说明这套 deck 要让观众相信什么。
2. 背景/现状:只保留理解问题所需的事实。
3. 问题/机会:用对比或数据说明为什么现在要行动。
4. 方案/发现:主体内容,按 3-5 个模块展开。
5. 影响/价值:把方案映射到业务、风险、成本、效率或体验。
6. 落地/下一步:时间表、责任、风险、请求。

## 常用模板

### 工作汇报

封面 → 本期结论 → 关键进展 → 数据/证据 → 风险与阻塞 → 下阶段计划 → 需要支持

适合周报、项目汇报、管理层同步。每个章节先给结论,再给证据。

### 方案/产品介绍

封面 → 痛点 → 目标用户/场景 → 方案总览 → 核心能力 → 架构/流程 → 价值 → 路线图

适合产品方案、内部平台、客户演示。不要从功能清单开始,先让痛点成立。

### 技术方案

封面 → 现状与约束 → 设计原则 → 总体架构 → 关键链路 → 方案取舍 → 风险与降级 → 演进计划

适合研发评审。每个设计选择都要回答“为什么不是另一种做法”。

### 审计/合规

封面 → 审计范围 → 方法与标准 → 总体风险画像 → 高风险发现 → 整改建议 → 责任与时限 → 附录

适合风险、合规、安全审计。风险等级、证据和整改动作必须绑定。

### 研究/分析

封面 → 问题定义 → 方法与数据 → 主要发现 → 解释与洞察 → 局限 → 建议/后续研究

适合分析报告。发现不要按数据源分组,要按洞察分组。

### 提案/决策

封面 → 决策请求 → 背景 → 备选方案 → 对比矩阵 → 推荐方案 → 成本/风险 → 决策点

适合需要拍板的材料。第一页就说清楚希望观众做什么决定。

## 页数与节奏

- 5 页以内:封面、结论、证据、建议、下一步。
- 6-10 页:允许 2-3 个章节,每章 1 张章节页 + 1-2 张正文页。
- 10 页以上:必须有目录或章节导航,否则观众容易迷路。

## 标题写法

标题是论点,不是栏目名:

- 弱: “现状分析”
- 强: “人工复核仍是审计瓶颈,高风险问题发现滞后”
- 弱: “方案架构”
- 强: “三类信息源先融合,再由智能体闭环补全证据”

## 素材取舍

- 用户给了很多文字时,先压成信息架构,再分页。
- 用户给了表格时,先找结论;只有查阅型附录才保留大表。
- 用户给了截图时,优先裁到关键区域,加标注或旁注。
- 只有当页内信息密度真的需要时,才使用附录。
